FWShift, feature by feature

FWShift converts firewall policies between thirty-one platforms, audits them, maps what each zone can reach, and proves from logs which rules are used. This guide walks through every feature, shows real commands and output, and lists, brand by brand, the cases where a conversion needs a human eye.

1What FWShift does

FWShift reads a policy into a neutral model of objects, security rules and NAT rules, then writes that model for another platform together with a report of everything that did not carry over exactly. The same model feeds the audit, the zone matrix and the rule-usage analysis.

The promise

A conversion never makes the policy more permissive without saying so. In practice:

  • Every source rule appears in the output, in the same order, or is listed in the report as skipped. Two counted exceptions: ASA entries that can never match (RULE_WITHOUT_EFFECT) and pfSense rules pfSense itself would not load (RULE_NOT_LOADED).
  • A rule the target cannot express is written disabled and marked needs review.
  • An object that cannot be converted becomes a placeholder that matches nothing, with FWSHIFT PLACEHOLDER in its comment.
  • Nothing that is missing is ever read as "any".

FWShift converts the policy. It does not convert interfaces, routing, VPN, users, security profiles or system settings, and it is not a substitute for testing.

Status. Tested against synthetic configurations. iptables and nftables output has been loaded on a real system (a Linux kernel, IPv4 filter rules, iptables 1.8.10 with the nf_tables backend, nft 1.0.9); FortiOS, PAN-OS, Cisco ASA, Juniper SRX and Cisco IOS XE output on a FortiGate-VM, a VM-Series, an ASAv, a vSRX a Catalyst 8000V, pfSense Plus and OPNsense, and AWS, Azure and Google Cloud output into real accounts, by the lab, for one synthetic policy with no NAT. Check Point output for that policy was published and verified on an R82.20 management server, by hand, but not installed on a gateway. Treat every other output, and NAT everywhere, as a draft for a lab device.

2Install and run

FWShift is on PyPI: pip install fwshift. Each release also has the project as a zip and a single file that runs with any Python 3.9 or newer. Nothing else needs installing.

shell
# one file, nothing to install
python3 fwshift-0.41.6.pyz --version
python3 fwshift-0.41.6.pyz convert running-config.xml --to fortios -o fortigate.conf

# or with pip, from PyPI
pip install fwshift
fwshift convert running-config.xml --to fortios -o fortigate.conf

The input may be - for standard input. The source format is detected (XML root elements, JSON keys, CLI keywords); give --from when detection could be ambiguous, for example --from ip6tables.

3A conversion, step by step

  1. Inspect what was read: counts, zones, and findings raised while reading.
  2. Convert with a report file, and read Notes for the whole policy first, then every rule marked needs-review. Disabled deny rules come first: the report says "This deny rule is NOT enforced until fixed".
  3. Re-run with the options the report asks for: --zone-map, --interface-map, --app-map, --zone-network, --target-prefix, --target-gateway, --target-nat-zone.
  4. Fix placeholders and disabled rules by hand.
  5. Load in a lab and test NAT first.
example
$ fwshift inspect tests/data/asa_sample.cfg

zones:           outside, inside, dmz, guest

  UNBOUND_ACL: 1 access lists are not bound with access-group ... branch_vpn
  VPN_BYPASS: the ASA lets traffic that arrives through its VPN tunnels past the interface access lists ...

4Commands

Seven commands share the source options. Only convert writes a configuration; the others read and report.

convert

Writes the policy for a target, with the report.

fwshift convert INPUT --to FORMAT

inspect

Shows what was read and what the parser had to say.

fwshift inspect INPUT

audit

Finds rules that allow too much, never match, or are unused.

fwshift audit INPUT

matrix

What each zone may reach in every other zone.

fwshift matrix INPUT

usage

Which rules, objects and services the logs show used.

fwshift usage INPUT --logs FILE

conduits

Checks the policy against a zone and conduit model, or drafts one.

fwshift conduits INPUT --model FILE

compare

Every connection two configurations decide differently.

fwshift compare FIRST SECOND

6Cross-platform rules

These differences hold whichever pair of platforms you convert between. Most findings in a report come from one of them.

Zones and interfaces

  • Names are kept as they are; rename with --zone-map.
  • PAN-OS, Sophos and FDM: zones are not created and must exist on the target (ZONES_REQUIRED). The FMC script creates missing zones, empty.
  • FortiOS: zones are created empty unless --interface-map fills them.
  • iptables and ASA have interfaces only: every zone needs a --zone-map entry (INTERFACES_REQUIRED).
  • PAN-OS intrazone and interzone rules become one FortiOS policy per zone, or per pair of zones.

Default behaviour

  • To PAN-OS: fwshift-intrazone-deny is appended, preceded by fwshift-intrazone-allow for zones that allowed intrazone traffic.
  • To FortiOS and Sophos: INTRAZONE_DEFAULT when the source allowed traffic inside a zone and the target does not.
  • A source that accepts what no rule matches keeps that only in iptables output (chain policy ACCEPT), ASA output (a final permit ip any any) and pfSense output (pass-all per interface). Elsewhere: INTERZONE_DEFAULT.

IPv4 and IPv6

  • FortiOS all is IPv4 only; PAN-OS any covers both. A FortiOS all-to-all becomes 0.0.0.0/0, not any.
  • Host names: FortiOS gets an IPv6 twin where needed; PAN-OS reports FQDN_FAMILY.
  • Sophos keeps one rulebase per IP version: rules become name and name_v6 (IP_VERSION_SPLIT).
  • iptables and ip6tables are separate programs: convert with both --to iptables and --to ip6tables (OTHER_IP_VERSION).

Negation

  • PAN-OS negates both IP versions at once; "not X" becomes a negated IPv4 list plus an IPv6 all. A FortiOS policy negated for one version only has no PAN-OS equivalent and is disabled.
  • ASA has no negation: the list is written as the ranges that are left (NEGATION_EXPANDED); a negated service gives SERVICE_NEGATE; a negated list with a host name, NEGATION_NOT_STATIC.
  • Cisco Secure Firewall: NEGATION_AS_ADDRESSES or NEGATION. Juniper: -excluded for up to 10 IPv4 addresses, else NEGATION_EXPANDED.

Names

Changed names are reported as RENAMED: 10.0.0.0/8 becomes 10.0.0.0_8 on PAN-OS, FortiOS policy names are cut to 35 characters, control characters become _.

What is not carried over

Security profiles, schedules, users, URL categories, HIP profiles and tags. When a rule's match depends on one, the rule is disabled; when it only adds inspection, the rule is approximated (PROFILES_NOT_CONVERTED, USER_MATCH).

7NAT order

The single biggest source of conversion surprises. Platforms disagree on whether a security rule sees the destination before or after destination NAT. The model follows PAN-OS: rules match the pre-NAT address and the post-NAT destination zone.

Security rules matchPlatformsWhat FWShift does
Before NAT (the original packet)PAN-OS, Check Point, Sophos 18+, SonicWallRules keep the public address.
After NAT (the translated packet)FortiOS, iptables (after PREROUTING), ASA 8.3+, FTD, pfSense, Juniper SRXRules are rewritten to the mapped address (NAT_DESTINATION_REWRITTEN), or the original is added next to it.

The same PAN-OS rule, written for three targets. The DNAT also changes the port from 443 to 8443, which no target rewrites for you:

PAN-OS source
set rulebase security rules Inbound-Web destination web-public      # 203.0.113.10, pre-NAT
set rulebase security rules Inbound-Web service service-https       # tcp/443
set rulebase nat rules Inbound-Web-DNAT ...                         # to web-1 10.20.0.10:8443
iptables
-A FORWARD -i eth0 -o eth2 -d 10.20.0.10/32 -p tcp -m tcp --dport 443 ... -m comment --comment "Inbound-Web" -j ACCEPT
-A PREROUTING -i eth0 -d 203.0.113.10/32 -p tcp -m tcp --dport 443 ... -j DNAT --to-destination 10.20.0.10:8443
Juniper SRX
set security policies global policy Inbound-Web match destination-address web-1
set security policies global policy Inbound-Web match application service-https
set security nat destination pool Inbound-Web-DNAT-pool address 10.20.0.10/32 port 8443
Check Point
m add access-rule layer Network_untrust_to_dmz position bottom name Inbound-Web destination.1 web-public service.1 service-https action Accept track.type Log
m add nat-rule package Standard position bottom original-destination web-public original-service service-https translated-destination web-1 translated-service tcp-8443 method static
Watch for. On iptables and Juniper the rule now names the mapped address but still the original port: the report raises NAT_PORT_TRANSLATION (needs-review). Change the service to tcp/8443 by hand.

Other NAT findings

  • NAT_ORDER: from FortiOS, iptables or ASA to PAN-OS, Check Point or Sophos, a connection that got DNAT and SNAT from two rules gets only the first on the target; from PAN-OS or Check Point to FortiOS or iptables, first-match NAT order is reported, not reproduced.
  • NAT_OUTPUT_INTERFACE, NAT_AFTER_DNAT: a rule that translates both destination and source.
  • NAT_ADDRESS_EXPOSED, NAT_DESTINATION_WIDENED, NAT_PORT_EXPOSED, NAT_EXEMPTION, NAT_OVERLAP: where the translated traffic is reachable in ways it was not.
  • A negated destination must name the same thing on both sides of the translation, or the rule is disabled.

8Applications and ports

PAN-OS rules match applications; most targets match ports. For FortiOS, Check Point, iptables and the others, an application on application-default becomes a service app-<name> from FWShift's own table (APP_TO_PORTS). That table is not Palo Alto's App-ID database.

  • An application not in the table disables the rule (APP_UNKNOWN). Add it with --app-map.
  • Explicit services on the rule win; the application match is dropped (APP_FILTER_DROPPED).
  • To PAN-OS, ICMP and IP-protocol services become applications (PROTOCOL_AS_APP). A single ICMP type becomes icmp, which matches every type (ICMP_TYPE).
  • Built-in entries include industrial protocols: modbus, dnp3, siemens-s7, bacnet, mqtt.
app-map.json
{
  "bittorrent": ["tcp/6881-6889", "udp/6881-6889"],
  "my-erp":     ["tcp/8000-8080"],
  "ping":       ["icmp/8", "icmp6/128"],
  "gre-tunnel": ["ip/47"]
}

Accepted specs: tcp/443, udp/53, sctp/2905, tcp/8000-8080, tcp/80,443, icmp/8, icmp/any, icmp6/128, icmp6/any, ip/47.

An unencrypted full configuration backup. Not show full-configuration output, which would flag nearly every rule. One VDOM per run.

Options

Source: --vdom. Target: --target-vdom, --policy-id-start N, --interface-map (zone members).

Output and loading

CLI configuration. If it holds config firewall vip or central-snat-map, enable central NAT first (config system settings, set central-nat enable, end) on a lab device: that changes how existing per-policy NAT translates. Assign interfaces to the zones the output creates. Policies use edit 0 and are appended; an object with an existing name is overwritten.

Watch for

  • A default service missing from the file is assumed to have its factory definition (FACTORY_DEFAULT).
  • NAT is written as central NAT (CENTRAL_NAT): source NAT as central-snat-map with IP pools, destination NAT as VIPs with extintf any, bi-directional static NAT as SNAT plus a VIP (NAT_BIDIRECTIONAL).

  • From FortiOS: a deny policy that covers a VIP without match-vip gives DENY_AND_VIP; NAT rules derived from policies ignore the policy's services (NAT_OVERLAP, NAT_EXEMPTION).
  • policy6 and local-in-policy are not converted (TABLE_NOT_CONVERTED); unknown attributes give UNKNOWN_ATTRIBUTES.
  • FortiOS all is IPv4 only: an all-to-all policy is not an IPv6 rule on the target.
  • Zones are created without interfaces (ZONES_WITHOUT_INTERFACES); intrazone behaviour differs (INTRAZONE_DEFAULT).

Watch for

  • IPv4 only: a rule with an IPv6 address is not converted (AZFW_IPV4_ONLY). To Azure Firewall, IPv6, source ports and ICMP types are left out of an allow rule and widened in a blocking one (AZFW_PART_NOT_WRITTEN, AZFW_BLOCKS_MORE).

  • Threat intelligence, IDPS and Azure's source NAT of traffic to public addresses are reported, not converted (AZFW_THREAT_INTEL, AZFW_SNAT).

When the logs prove a rule unused

No connection proves a rule unused only when all of these hold. Otherwise the finding is NO_USAGE_EVIDENCE with the reasons.

  • The rule logs its connections (see the table above).
  • It was not created or changed within the window: from Check Point meta-info, PAN-OS hit counters, or your word with --unchanged-since.
  • Every gateway it is on logged connections on every day of the window, with at least one accepted connection. For a policy of a vsys or VDOM, only that vsys or VDOM's lines count.
  • No line of those gateways could not be read, and no log said lines were lost.
Certain and possible. An iptables line names no rule, so it is matched against the rules in order: certain for the first rule that surely matches it, possible for every rule it may have gone through (a -m limit rule, a negation that cannot be read). The same holds for a PAN-OS session start without its end. A rule with only possible connections is never called unused.

Watch for

  • PAN-OS: a rule only the first packets of a session match (an application dependency) appears in start logs only; with logging at session start off, its use is not seen.
  • PAN-OS logs local time; lines of 10.0 and later carry a zone in the high-resolution timestamp. Older lines need --log-offset.
  • FortiOS before 6.4: IPv6 policies (policy6) had their own IDs; a log may name an ID that is an IPv4 policy's. UUIDs avoid this.
  • Several firewalls in one log file and no --gateway: a rule found by name or policy ID (not UUID) is possible only.
  • iptables lines carry no verdict; NFLOG and ULOG go to ulogd and are not read; dmesg keeps neither time nor host.
  • Two exports that overlap count shared connections twice: counts grow, no rule is called unused by it.

15Narrower rules

A used allow rule whose connections used at most 10% of a cell (threshold wider_than_traffic) gets WIDER_THAN_TRAFFIC with a narrower rule: the same rule with its sources, destinations and services cut to what was used. A proposal is never wider than its rule and holds every connection the logs show, possible ones included.

usage report
  [low] WIDER_THAN_TRAFFIC: rule 'LAN web' had 90 connection(s) from 2026-07-03 to 2026-09-30, which used of its
        sources less than 0.01% of what they hold ('10.10.4.20/32'); ...

Narrower rules
  'LAN web-narrowed' for 'LAN web': sources 10.10.4.20/32; destinations 203.0.113.200/32; services tcp/443 (the rest as it is)
  'LAN DNS-narrowed' for 'LAN DNS': sources 10.10.4.20/32; destinations 192.0.2.53/32 (the rest as it is)
  • Addresses are grouped into /24, then /16 networks (IPv6 /64, /48) while there are more than 16, and cut back to the cell.
  • A cell is left as it is when it holds a host name or an unreadable object, is negated, names a destination NAT, or when a connection left its address or port unknown.
  • No proposal for blocking rules, rules whose logs prove nothing, rules read approximately, or parts of a split rule. Zones, applications and users are not narrowed.
shell
fwshift usage rules.v4 --logs kern.log --log-year 2026 --unchanged-since 2026-01-01 --propose narrow.json
fwshift usage rules.v4 --logs kern.log --log-year 2026 --unchanged-since 2026-01-01 --propose narrow.rules --propose-to iptables
Take the rules out; do not load the file. --propose writes the neutral model by default. A --propose-to file is a conversion of a policy holding only the narrowed rules, and the emitter adds what its target needs around them: a whole table for iptables-restore, a layer ending in a cleanup Drop (Check Point), access groups (ASA). Copy the <rule>-narrowed rules into place, check FILE.report.txt, then disable the original.

A proposal only knows the window: a quarterly job the logs did not see is not in it. Choose a window that covers the rule's whole cycle.
